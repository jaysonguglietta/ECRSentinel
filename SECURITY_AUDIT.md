# ECR Sentinel — adversarial security audit

**Date:** 21 October 2026  
**Scope:** server.js; src/api.js, src/aws-cli.js, src/trivy.js; scripts/generate-sbom-bundle.mjs; public/index.html, public/app.js, public/auth-guide.js, public/styles.css; package.json, package-lock.json, and tests.  
**Method:** file-by-file source review, threat model, 31 automated tests, real Trivy CLI checks and a public Alpine image scan, and desktop/mobile browser inspection. The in-app MFA path was tested with a simulated credential provider and AWS CLI runner; no private ECR image, build-host generated SBOM, or live MFA challenge was available.

## 1. Executive Summary

ECR Sentinel uses AWS CLI to discover private ECR images. It can ask Trivy to scan an exact image digest on the Mac when the profile has pull access, or import a build-host SBOM bundle and run Trivy against its listed packages without transferring image layers to the Mac. It does not use ECR managed scanning APIs. The design is for one local operator. A private launch link authorizes the browser. For a simple role profile with `mfa_serial` and one source profile, the browser now accepts a six-digit code; the local Node process passes it to the AWS SDK credential provider and keeps the resulting temporary role credentials in memory. A timer removes them one minute before STS expiration; lookup also rejects expired or changed-profile sessions. Unsupported role chains and other sign-in methods retain their Terminal flow. Trivy receives resolved AWS credentials only during direct image scans. SBOM checks pass no AWS credentials to Trivy. The browser receives no AWS access key or session token, and it does not save the MFA code in browser storage or reports.

No confirmed remote code execution, injection, authentication bypass, OTP disclosure through command arguments, or cross-account report leak remains in this build. The review found and fixed token disclosure to other local OS users, acceptance of vulnerable Trivy versions, excessive report retention, overstated package coverage, account/platform report-integrity defects, a mutable-tag SBOM generation race, unbounded build-host SBOM output, and concurrent large-upload buffering. Five open limitations are detailed below. The leading risks are unverified SBOM-to-image attribution and resource exhaustion while processing untrusted image or SBOM content. The new local MFA route makes the launch token and same-user browser/process trust boundary more consequential because an authenticated role session can remain in the Node process after the current tab is locked.

This loopback application is **not ready to be exposed as a hosted or multi-tenant service**. A reverse proxy or public bind would require a new authentication, authorization, audit, and abuse-control design.

## 2. System Overview and Trust Boundaries

Browser MFA input → protected loopback POST → AWS SDK role-profile resolver → AWS STS temporary credentials held in Node memory → credential-isolated AWS CLI calls. Existing AWS CLI Terminal sign-in and its separate role cache remain available. In direct mode, one local worker updates Trivy databases without AWS credentials, resolves selected-profile credentials, and asks Trivy to read the ECR digest. In SBOM mode, an authorized build host first uses Docker and Trivy to generate a CycloneDX bundle from a locally available final image. The operator transfers that file to the Mac; the loopback API checks its declared account, Region, repository, digest, and platform, then asks Trivy to check the SBOM without AWS credentials or ECR layer access. Trivy returns JSON; Node normalizes both report types into memory; the browser displays findings and can export CSV.

**Assets:** the one-time MFA code during the request, AWS source-profile credentials and temporary role sessions in Node memory or AWS CLI cache, and the authority to list and pull private images; repository/tag/digest metadata and image layers; SBOM package inventory and its claimed producer/target; report accuracy and provenance; the launch token; Trivy databases and analysis cache; exported CSV files.

**Trust boundaries:** local browser, including an MFA code entered by the operator, and selected SBOM file to the loopback API; request fields to AWS CLI/Trivy arguments; trusted local AWS config/source credentials to the SDK role resolver; temporary role credentials in Node memory to isolated AWS CLI/Trivy children; ECR manifests/layers, imported SBOM JSON, and public DB artifacts to Trivy; authorized build host/Docker image to transferred bundle; report text/URLs to DOM and CSV; and owner's Terminal to browser for the launch secret. The Mac account, AWS CLI/Trivy binaries, AWS SDK packages, profile credential providers, DNS/proxy/CA settings, VPN, and any authorized build host are trusted dependencies. Bundle metadata is untrusted until independently verified against a trusted producer; this version does not do that verification.

## 3. Threat Model

| Attacker | Plausible path | Current boundary |
|---|---|---|
| Malicious website | Cross-site localhost requests, DNS rebinding, CSRF | Exact Host/Origin checks, no CORS, private API token, CSP |
| Another local OS user | Connect to predictable loopback port as app owner | Static page does not reveal token; private launch fragment is shown in owner's Terminal |
| Local process or person with the launch token | Trigger AWS actions using an already authenticated role session, or submit MFA codes if available | Local single-operator boundary; one MFA request globally, five attempts per profile per minute, no server-side token revocation from Lock this tab |
| ECR image publisher | Crafted layer, tags/package names, huge image, multi-platform ambiguity | Digest/registry/platform checks, DOM text insertion, CSV formula escaping, bounded single-worker scan |
| Malicious or compromised SBOM source | Omit vulnerable packages or assert a false image digest/platform/producer | Exact declared-target comparison, size/complexity limits, no-credential Trivy child, visible unverified-association warning; no signature verification |
| Compromised build host or Docker daemon | Generate a false inventory or tamper with its target claims | Helper checks local ECR RepoDigest, scans a pinned Docker image ID, checks platform and image ID again; host and artifact transfer still require trust |
| Compromised scanner or local profile | Read credentials or redirect network calls | Trusted local dependency; scanner version floor, fixed command/flags, environment filtering, least-privilege IAM needed |
| Malicious DB mirror or network path | Poison downloaded vulnerability data | TLS and Trivy default DB sources; app disables local Trivy config and inherited overrides; local proxy/CA still trusted |
| Malware under same Mac user | Read browser session, AWS CLI cache, or Node process memory | Outside the app's isolation boundary; workstation and short-lived IAM controls required |

There is no SQL/NoSQL database, multipart or archive parser, template engine, LDAP client, webhook receiver, arbitrary user-provided URL fetcher, billing flow, multi-tenant data model, or configured deployment pipeline in this codebase. SBOM upload is bounded JSON, and the build-host helper is a script that must be integrated into an authorized build process. The other categories were checked for reachable paths and are not applicable here.

## 5. Prioritized Findings

### F-01 — Trivy lacks an OS-level resource boundary

- **Severity / confidence / status:** Medium / High / Open defense-in-depth gap. No Trivy exploit was demonstrated.
- **Affected files/functions:** src/trivy.js, runBounded, TrivyScanService.runJob and runSbomJob; scripts/generate-sbom-bundle.mjs, generateSbomBundle.
- **Description and code evidence:** the Mac runs one Trivy job at a time with a 15-minute child deadline, experimental 4 GB image-size flag, 16 MiB SBOM input cap, and output/finding caps. The build-host helper also pins an image ID and bounds CycloneDX stdout at 16 MiB. Neither process has an OS memory, CPU, decompressed-data, or cache-disk quota.
- **Exploitation scenario:** an adversary supplies a heavily compressed ECR layer or parser-stressing SBOM that an operator scans. The Mac or build host exhausts memory or temporary disk before the child deadline or output cap applies.
- **Potential impact:** local denial of service, interrupted work, disk pressure, and loss of unsaved in-memory reports. This is not evidence of code execution.
- **Recommended fix and patch guidance:** run Trivy in a separate OS worker/container with memory, CPU, and disk ceilings and a scoped cache on both the Mac and build host. Until then, monitor cache size and preserve resource-limit failures as incomplete rather than converting them to zero findings.
- **Validation:** scan controlled decompression-heavy images and complex SBOM fixtures while measuring child RSS, CPU, and cache growth; assert worker termination and recovery of queued jobs.
- **Category:** CWE-400, uncontrolled resource consumption.

### F-02 — Imported SBOM attribution is unsigned and package completeness is unverified

- **Severity / confidence / status:** Medium / High / Open conditional integrity limitation; no forged bundle was accepted from a real build pipeline in this review.
- **Affected files/functions:** scripts/generate-sbom-bundle.mjs, generateSbomBundle; src/trivy.js, validateSbomBundle and runSbomJob; public/app.js, SBOM provenance and CSV export.
- **Description and code evidence:** the helper checks that Docker associates the selected local image with the stated ECR RepoDigest, pins Trivy to the inspected Docker image ID, and rechecks that ID. On import, the API compares bundle-declared account, Region, repository, digest, and platform with the selected ECR image and checks that the digest exists. These are consistency checks on data supplied by the bundle and local build host. The bundle has no signature or independently verified attestation binding its package list and per-platform image identity to a trusted producer. The UI and exported report label this association unverified.
- **Exploitation scenario:** a compromised artifact transfer route or build host substitutes a CycloneDX/SPDX bundle that declares the selected digest and platform but omits vulnerable packages. Trivy accurately reports no matching CVEs among the listed packages, while the deployed image still contains vulnerable packages.
- **Potential impact:** false confidence in a report attributed to the wrong or incomplete image inventory, especially if an exported CSV is used as a deployment gate without its provenance warning.
- **Recommended fix and patch guidance:** have the authorized build process generate an attestation whose subject is the immutable ECR manifest digest, including a child manifest digest for each platform of a multi-platform image. Sign it with an approved CI identity and verify the signature, issuer/identity, subject digest, and SBOM hash before marking an association verified. Keep unsigned imports visibly unverified and exclude them from any automated pass/fail gate.
- **Validation:** import a bundle with the selected declared target but substituted package contents; confirm it remains unverified. Then test valid, altered-content, wrong-subject, wrong-platform, and untrusted-signer attestations once verification is implemented.
- **Category:** CWE-345, insufficient verification of data authenticity; OWASP A08 Software and Data Integrity Failures.

### F-03 — Offline dependency resolution can omit Java packages

- **Severity / confidence / status:** Medium / High / Open coverage limitation.
- **Affected files/functions:** src/trivy.js, TrivyScanService.runJob, runSbomJob, and normalizeTrivyReport; scripts/generate-sbom-bundle.mjs, generateSbomBundle; public/app.js provenance and empty states.
- **Description and code evidence:** direct ECR scans use Trivy's offline-scan flag so the scanner cannot query Maven services while AWS credentials are present. SBOM generation and checking also use offline resolution, and an imported SBOM can omit packages before the Mac receives it. The report distinguishes SBOM package-list coverage from direct image coverage. [Trivy's Java coverage guide](https://trivy.dev/docs/latest/coverage/language/java/) explains that some pom.xml dependencies need remote lookup.
- **Exploitation scenario:** an image contains a vulnerable Java dependency expressed only in metadata needing remote resolution. Trivy completes with fewer detected packages, perhaps no match for that dependency.
- **Potential impact:** a low- or zero-finding report may be mistaken for full language-package coverage.
- **Recommended fix and patch guidance:** retain the visible coverage warning, mark unresolved dependency files as incomplete, and avoid treating SBOM zero findings as proof about packages missing from the bundle. A stronger direct-scan design fetches the exact image with scoped ECR authority, drops credentials, then allows Trivy to use a controlled Maven network path during analysis.
- **Validation:** build a pom-only Java image with a known dependency and compare this app's report with a credential-free online Trivy scan; assert any missing coverage is labeled.
- **Category:** OWASP A04 Insecure Design; CWE-693 protection-mechanism gap.

### F-04 — Long-lived IAM keys can enter the direct image scanner process

- **Severity / confidence / status:** Medium / High / Open conditional credential-exposure design gap. No compromise of the installed scanner was observed.
- **Affected files/functions:** src/aws-cli.js, exportCredentials; src/trivy.js, scannerEnv and runJob.
- **Description and code evidence:** AWS CLI export-credentials can return static AKIA IAM-user keys as well as temporary role/SSO credentials. The new in-app MFA path obtains only a temporary role session, but other configured profiles can still supply static keys. The app accepts both and passes resolved keys to the Trivy child environment for direct image scans. SBOM scans do not pass AWS credentials. Browser, command arguments, DB refresh, and app errors do not receive the secret, but direct Trivy image scans process untrusted content while holding it.
- **Exploitation scenario:** a compromised scanner binary or future image-parser vulnerability reads its environment. If the selected profile has a static key, the credential remains useful after the scan.
- **Potential impact:** AWS access within that profile's IAM permissions and credential lifetime.
- **Recommended fix and patch guidance:** prefer least-privilege mfa_serial role or Identity Center profiles. For high-risk use, require a session token and future Expiration before scan, or split authenticated image retrieval into a low-privilege broker and scan a private artifact after credentials are removed.
- **Validation:** use disposable static and temporary profiles; verify the chosen policy rejects/warns on static keys and that no credentials appear in browser state, CSV, logs, error bodies, or child arguments.
- **Category:** CWE-522, insufficiently protected credentials.

### F-05 — Persistent scanner cache and crash residues have no complete retention control

- **Severity / confidence / status:** Low / High / Open operational and privacy gap.
- **Affected files/functions:** src/trivy.js, ensureCache/privateDirectory and runSbomJob; README.md Local data and retention.
- **Description and code evidence:** the owner-only cache is reused across server restarts and can contain vulnerability DBs plus image analysis data. On this Mac, vulnerability and Java DBs together used about 3 GB. A temporary SBOM file is mode 0600 and removed in runSbomJob's finally block; on cache initialization, matching owned files older than one hour are swept. A hard kill can still leave an SBOM file until a later startup and age threshold. There is no cache-size display, expiration policy for analysis data, or clear-cache action.
- **Exploitation scenario:** repeated scans consume temporary disk; an operator assumes stopping the app immediately erases SBOM contents when a crash has left a private file behind.
- **Potential impact:** disk pressure and longer inventory retention. Mode 0700 directory, mode 0600 file, and ownership checks mitigate cross-user reading.
- **Recommended fix and patch guidance:** use a per-run private SBOM directory and remove it on clean shutdown, retain the stale-file sweep for crashes, and document that hard kills can leave data until cleanup. Add an idle-only cache-size display and explicit clear action with TTL or quota. Before recursive removal verify the exact app path, owner, directory type, and non-symlink status.
- **Validation:** create a private test cache and orphaned SBOM file, restart to verify the one-hour sweep, clear when idle, and confirm only the app-owned cache is removed.
- **Category:** CWE-400; CWE-922 sensitive-information retention.

### Issues fixed during this review

- **Role MFA entered in the app without OTP in child arguments:** the POST endpoint requires the local launch token, exact Host/Origin, JSON body, a listed profile, valid Region, and six digits. The backend permits only a simple role with one source profile and checks its configured MFA serial; unsupported role chains retain Terminal sign-in. The AWS SDK `fromIni` callback receives the code in process memory. The code is not passed to an `aws` command argument or child environment, saved to browser storage, or returned in the API response. Before accepting credentials, the backend checks expiration, configuration stability, and the STS caller's role/account. Inventory calls then omit `--profile` and use an isolated child environment. Five attempts per profile per minute and one in-flight MFA request globally bound local guessing and request amplification. This was verified with a simulated provider and CLI runner, including cross-profile concurrency, not a live MFA challenge. CWE-522 / OWASP A07.
- **Shared-Mac token disclosure:** previously, any GET / embedded the API bearer token in HTML, allowing another local OS user to use the owner's AWS profile. Static HTML is now token-free; server startup prints a private URL fragment in the owner's Terminal; the browser moves it into session storage and removes the fragment from the address bar. API calls still require the header. This is not protection against malware under the same OS account. CWE-306 / OWASP A01.
- **Unsafe scanner versions:** the initial guard accepted the malicious Trivy 0.69.4 release and older releases with a conditional OCI artifact path-traversal issue. The guard now requires stable Trivy 0.71.1 or newer. Installed Homebrew Trivy 0.76.0 passes. See [Aqua's supply-chain advisory](https://github.com/aquasecurity/trivy/security/advisories/GHSA-69fq-xp46-6x23) and [path-traversal advisory](https://github.com/aquasecurity/trivy/security/advisories/GHSA-mcj4-mphf-j9ff). The path-traversal advisory requires a non-default attacker-controlled artifact source; this app strips Trivy overrides.
- **Report retention DoS:** completed job objects initially held full reports in addition to a ten-report map. Jobs now hold metadata and tests verify eviction of full results. CWE-400.
- **Scanner-status process flood:** repeated status requests initially launched a new Trivy version process each time outside the scan queue. The endpoint now deduplicates concurrent checks and caches outcomes for 30 seconds; a test submits 12 concurrent requests and observes one child. CWE-400.
- **Coverage and account integrity:** coverage derives OS/language classes from actual Trivy Results and identifies no-package reports. Jobs are keyed to resolved AWS account, recheck account before scan and credential use, validate repository URI and digest, and check actual platform. Tests cover changed account and architecture mismatch. CWE-754 / OWASP A04.
- **Build-host tag race and output growth:** the SBOM helper initially inspected a mutable Docker tag but gave that tag to Trivy. It now scans the inspected immutable Docker image ID, rechecks the tag-to-ID binding, limits the image to 4 GB, and bounds CycloneDX stdout to 16 MiB before writing the private bundle. Tests cover tag swaps and oversized output. CWE-367 / CWE-400.
- **Concurrent SBOM upload buffering:** the new JSON endpoint initially accepted multiple 20 MiB uploads before the three-job queue check. It now permits only one active SBOM upload and rejects another with 429 before reading its body. The server still caps each upload by declared and actual bytes. CWE-400.
- **Bundle report identity:** separate SBOM and direct-image job modes prevent an imported SBOM report from being silently presented as an image-layer scan. The SBOM content hash and a hash of validated bundle target/producer metadata are recorded separately; the latter keys duplicate SBOM jobs so a changed producer claim does not reuse a previous job's provenance. These hashes identify bytes and claims, not authenticity. CWE-345.

## 6. Exploitation Chains or Combined-Risk Scenarios

1. **Malicious ECR image + unsandboxed scanner:** image publisher controls layers parsed by a process with the selected AWS profile's ECR authority. Version checks and bounds reduce known risk; OS isolation and temporary credentials are the next boundary.
2. **Static IAM key + compromised scanner:** a static key exported from a profile can remain valid long after the scan. Role MFA and short sessions reduce the useful window.
3. **Forged SBOM + apparently clean report:** an attacker who controls an unsigned bundle can provide a matching digest claim and omit vulnerable packages. ECR metadata confirms the selected digest exists but cannot prove those packages came from it. The UI's unverified warning must survive export and any future policy integration.
4. **Offline Java lookup + zero findings:** a completed direct or SBOM scan can have no matched advisories while some dependencies are unresolved or absent from the inventory. Coverage notes must remain attached to reports and zero must never be presented as proof of safety.
5. **Future public bind + bearer model:** a reverse proxy would turn the local launch secret into shared access with no operator identity, tenant authorization, or audit trail.
6. **Stolen launch token + existing role session:** the browser's Lock this tab action clears this tab's token and code field, but neither rotates the server's launch token nor revokes its in-memory role credentials or AWS CLI cache. Someone who already obtained the token while the server remains running can continue to use the local API and any still valid session. Stop the server to discard its in-memory session; rotate/revoke AWS credentials through AWS if compromise is suspected.

## 7. Dependency and Configuration Risks

- The in-app MFA flow adds `@aws-sdk/credential-providers` and `@smithy/node-http-handler` as runtime dependencies, with resolved transitive packages and integrity hashes in package-lock.json. `npm audit --omit=dev` reported zero known advisories in the installed dependency graph on 21 October 2026; that is a point-in-time database check, not proof that a dependency is safe. Use `npm ci` from the lockfile and review updates before release. Node.js, AWS CLI, Homebrew, and Trivy remain system dependencies requiring trusted distribution and patching. The app blocks Trivy below stable 0.71.1, but does not attest binary hashes.
- The build-host helper requires a trusted Docker daemon and local final image associated with the exact ECR RepoDigest. It strips inherited AWS and Trivy configuration from its child environment, checks the scanner version, uses a pinned Docker image ID, and refuses to replace an existing bundle. It is not an installed CI job or signed release pipeline; the operator must run it on an authorized host and deliver the file through an approved channel.
- Database integrity/freshness depends on Trivy's default OCI registries, TLS, and local proxy/CA settings. The app clears inherited Trivy/Docker configuration and disables local trivy.yaml and .trivyignore. It does not independently sign or attest DB artifacts.
- AWS CLI profiles may invoke credential_process or use cached role/SSO/login sessions. A compromised local profile affects ordinary CLI use too. The in-app MFA route rejects credential_process and chained/extra MFA settings in the selected role and its source profile, then uses SDK `fromIni` only for this simple configuration. It does not populate the AWS CLI role cache. Its role credentials live in the Node process and are passed through isolated child environments for AWS inventory or direct Trivy scans. The app refuses cli_history=enabled because CLI history may persist sensitive API responses. Network proxy, CA, and local source credential files remain part of the trusted Mac environment.
- Direct ECR pulls need ecr:GetAuthorizationToken, ecr:BatchGetImage, and ecr:GetDownloadUrlForLayer alongside inventory actions. The Mac's SBOM path uses ECR metadata and needs no layer-pull permission, but the authorized build host must have access to the final image. Direct mode needs VPN reachability to the ECR registry and S3 layer URLs. Both modes need reachability to Trivy's default DB registries; an internal mirror requires an app change.
- No configured CI/CD job, container deployment, reverse proxy, or release-signing configuration exists here, so hosted hardening and release provenance were not verifiable.

## 8. Secure Design Gaps

There are no app user accounts, per-operator audit records, central triage, exception approvals, deployment gate, scheduled rescan, malware scan, secret scan, or verified SBOM attestation. This is a local single-operator tool. Lock this tab only clears that browser tab's token and MFA field; it does not revoke the server launch token, active in-memory role session, or AWS CLI cache. A timed-out SDK sign-in is rejected by the app, but its `Promise.race` deadline does not itself abort the underlying SDK operation; the STS HTTP handler has shorter request/connect limits and no late result is stored. A future explicit abort signal would make timeout behavior easier to reason about. The helper produces an unsigned bundle; neither the browser nor backend can prove that an imported package inventory was produced by the authorized build host or represents the selected digest. Reports disappear on restart; Trivy cache persists. Findings are package-advisory matches for one selected platform and one vulnerability DB snapshot. In SBOM mode they cover only packages present in the imported file. These are product-scope limits, not evidence that the missing capabilities were attempted.

## 9. Recommended Remediation Roadmap

1. **Before operational reliance:** exercise the in-app MFA path with a disposable least-privilege role and real six-digit challenge, including valid, wrong, expired, and reauthentication codes, then run inventory and a direct scan using that session. Run the build-host helper on an authorized final image, transfer its bundle through an approved route, and compare its SBOM report with a direct scan where pull access exists. Test a populated private ECR repository, both platforms, ECR/S3 network routes, Java DB behavior, and zero findings. Keep unsigned SBOM reports out of automated deployment gates.
2. **Provenance iteration:** sign the SBOM attestation in the authorized build process and verify the trusted producer identity, SBOM hash, ECR subject digest, and platform-specific child digest on import. Reject or visibly quarantine mismatches.
3. **Next security iteration:** isolate both Trivy modes and the build-host helper with resource ceilings, require temporary credentials for direct scans in high-risk environments, and add cache-size/clear and crash-retention controls.
4. **Coverage iteration:** separate authenticated image retrieval from dependency analysis so Java lookup can run without AWS credentials; label unresolved or omitted SBOM dependencies as incomplete.
5. **Team or hosted use:** add real user authentication, per-user/account authorization, durable audit logs, retention, global abuse limits, server-side session revocation, and a deployment-specific threat model.

## 10. Security Test Plan

**Performed:** 31 automated tests for CLI profile and MFA handling, fixed AWS arguments, absence of ECR managed-scan API calls, credential export, credential-free DB refresh and SBOM scanning, scanner version floor, repository/account/digest/platform validation, SBOM bundle mismatch and size limits, build-host image-ID pinning and output cap, one-active-upload rejection, report normalization and eviction, scan cancellation, and token/Host/Origin/body limits. New MFA tests use a simulated SDK provider and CLI runner to check protected POST handling, six-digit input, rejection of unsupported role chains and extra MFA prompts, cross-profile concurrency, in-memory reuse, and absence of the code in child arguments/environment/API output. Syntax checks, a public Alpine Trivy 0.76.0 image scan, and desktop/mobile browser inspection were also performed. `npm audit --omit=dev` reported zero known advisories in the installed graph. The public image scan produced schema-version-2 JSON. A real build-host generated bundle, private ECR scan, and live MFA challenge were not available.

**Add before high-risk deployment:**

- From a second macOS account, fetch / and API endpoints; verify no token or inventory access without the launch secret. Test wrong Host, Origin null, rebinding, stale token, and browser fragment removal.
- Exercise uncached and cached role `mfa_serial`, valid/wrong/expired OTP, role reauthentication after expiration, unsupported chained profiles, SSO, static IAM key, and credential_process with disposable accounts. Verify the in-app path does not write an AWS CLI role cache, and no credentials/OTP appear in browser storage, CSV, logs, error bodies, or child arguments.

- Crash the app during an SBOM check, restart after the one-hour stale threshold, and verify only matching owner-owned temporary SBOM files are removed; inspect persistent cache for residual package data.
- Simulate DB outage, ECR/S3 failure, cancellation in every phase, timeout, oversized output, and cache permission/symlink failure; ensure none appears as a clean report.
- Use a controlled decompression-heavy image to verify resource ceilings once implemented.

## 11. Open Questions and Assumptions

- The Mac is primarily single-user; another process under the same OS account is not isolated from browser/session or AWS CLI credentials.
- Which accounts, Regions, repositories, and platforms need routine scans? The live development profile had no repositories in the checked Region.
- Do the target MFA profiles all have a simple `source_profile`, or do some use role chaining, `credential_source`, `credential_process`, or extra MFA? The app keeps the Terminal path for those configurations until their flows are explicitly designed and tested.
- Should Lock this tab only hide the current browser session, as labeled, or must it revoke the server launch token and invalidate temporary role sessions? Revocation would need a distinct server action and a new launch link.
- Which build platform and artifact-transfer route can run the included helper on the final locally available image and deliver the bundle to the Mac? No CI pipeline was provided or configured.
- Must SBOM reports be admissible for deployment decisions? If so, which CI identity and signing/attestation system should be trusted, and how will multi-platform child digests be recorded?
- Are temporary role/SSO credentials mandatory, or are static IAM keys allowed for this tool?
